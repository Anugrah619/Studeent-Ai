Named choices, with the alternative that lost

The Django call, specifically

This product is unusually admin-heavy: someone has to confirm question→topic mappings, edit per-institute syllabus trees, resolve duplicate students and onboard tenants. In FastAPI each of those is a small application you build and maintain. In Django they are a ModelAdmin class each. That single fact is worth more than every ergonomic argument on the other side.

03 — The nine stages

What you build, and what you build it with
P0

Syllabus tree & canonical schema

≈ 1–2 weeks

The foundation everything references. Get it wrong and every later stage inherits the mistake; there is no cheap fix once real attempt data is bound to it.

Build
  • Exam → subject → unit → topic tree, versioned per institute
  • Append-only event tables with tenant_id on every row
  • Multi-tenant skeleton with Postgres RLS policies
  • Django admin for tree editing and tenant onboarding
Tech
  • django 5 + DRFProject skeleton, custom user model from day one — swapping it later is a migration nightmare
  • postgres 16ltree or adjacency list for the tree; ltree if you want cheap subtree queries
  • RLS policiesTenancy enforced in the database, not in a Django manager someone forgets to use
  • django-environConfig from environment; no settings committed
Trap: a single global syllabus tree. Two Kota institutes teaching JEE split and name chapters differently. Version per institute with a canonical mapping underneath, or your second customer forces a rewrite.
Done when: you can create two institutes with different trees, and a query as institute A provably cannot return institute B's rows.
P1

Roster & mock result ingestion

≈ 4–6 weeks

The largest engineering surface in the project, and the one everyone underestimates. Every institute exports differently; names have three spellings; roll numbers collide across batches; half the papers carry no chapter tags.

Build
  • File upload with format sniffing (xlsx / csv / vendor OMR exports)
  • Per-institute column-mapping profiles, stored as JSONB and reused
  • Identity resolution: exact on roll number, fuzzy on name, human queue for the rest
  • Question→topic mapping tool with a review queue in Django admin
  • Idempotent re-import — the same file twice must not double every attempt
Tech
  • pandas + openpyxlParsing. Stream large files rather than loading whole sheets
  • rapidfuzzName matching — far faster than fuzzywuzzy, same API shape
  • celeryIngestion is a job, not a request. Never parse a file in a web worker
  • django adminThe mapping review queue. This is the payoff for the framework choice
  • jsonbColumn-mapping profiles and raw row snapshots for replay
Trap: building OMR sheet scanning. Nearly every institute already has an OMR vendor that exports CSV. Build the importer, not the scanner — this decision alone saves a month.
Done when: an institute's real historical mock file imports end-to-end, unmapped questions land in the queue, and re-importing the same file changes nothing.
P2

Feature store & mock analyzer

≈ 2–3 weeks

Where the system starts knowing things nobody told it. Rung-0 mastery only — a time-decayed rolling accuracy per (student, topic), computed in SQL.

Build
  • topic_state and student_state, recomputed on event and nightly
  • Marks-lost attribution: conceptual gap · execution error · time exhaustion · avoidable skip
  • Time-per-question baselines per student
  • Full rebuild-from-events command, so state is always reproducible
Tech
  • postgres windowsOVER (PARTITION BY student, topic ORDER BY ts) — the whole of rung 0. No ML library
  • materialized viewsCohort aggregates; refresh nightly via beat
  • celery beatNightly recompute, idempotent and replayable
  • pytestGolden-file tests: known event stream in, known feature values out
Done when: you can drop all derived tables, replay the event log, and land on byte-identical state.
P3

Detectors, mentor console, director dashboard

≈ 3–4 weeks · FIRST SALE

The first thing anyone will pay for, and demonstrable on an institute's historical files with no student onboarding at all. This is the pilot.

Build
  • Tier-0 detectors: weak topic, over-attempting, plateau
  • Evidenced flags with severity, routed to a named mentor
  • Intervention logging and outcome tracking — the loop must close
  • Director view: institute health, batch comparison, at-risk triage list
  • Alert hygiene: minimum evidence, personal baselines, cooldown windows
Tech
  • htmx + alpineServer-rendered tables, filters, drill-downs. No API layer, no build step
  • echartsTrend lines and heatmaps; loaded from CDN, configured server-side
  • django templatesShared with the PDF renderer later — write them once
  • detector registryEach detector a class with evaluate() returning evidence; version the rule so flags stay auditable
Trap: firing flags on thin evidence. Three wrong answers is noise. A console that cries wolf in week one is ignored by week three, and you will not get a second chance with that mentor.
Done when: you can load a real institute's last six months and show its director five students they did not know were in trouble — with the evidence for each.
P4

Student app & study logging

≈ 3–4 weeks

All the adoption risk in the product lives here. The design constraint is friction, not features: a log form that takes three minutes collects nothing by week three.

Build
  • Daily log capture in under forty seconds — topic, minutes, mode
  • Chapter self-rating (1–5) for the confidence signal
  • Personal dashboard: consistency, subject balance, mock trend
  • Web push for the daily nudge
Tech
  • PWAInstallable, no app store. Svelte or vanilla + Vite — the surface is small
  • service workerOffline log capture, queued and synced. Students log on patchy data
  • web push + VAPIDWorks on Android Chrome, which is the overwhelming majority of this market
  • DRF + JWTThe API layer finally earns its place here
Trap: shipping native apps first. App-store review between you and a pilot fix is an unnecessary tax before adoption is even proven.
Done when: median daily log time is under forty seconds and week-3 retention in the pilot batch is above half.
P5

Retention model & revision scheduler

≈ 2–3 weeks

Per-topic decay estimation and the revision cycle queue — with the deadline modification that no existing library provides.

Build
  • Per-topic retention estimate with decay since last touch
  • Revision cycles R1 / R2 / R3 with due dates
  • Deadline-aware interval compression as the exam approaches
  • Revision debt as a first-class metric on both consoles
Tech
  • py-fsrsStarting point. You will fork it — the objective function differs
  • custom objectiveMaximise recall probability on exam date, not minimise lifetime reviews
  • scipy.optimizeFitting decay parameters per student once you have volume
Genuinely novel work

Anki-lineage schedulers assume indefinite retention with minimum review cost. Exam prep inverts that: fixed syllabus, hard deadline, finite hours. Topics whose forecast recall on exam day is already sufficient should be deprioritised. Budget research time, not install time.

P6

Daily planner

≈ 2–3 weeks

Four prioritised queues competing for a fixed number of minutes, under constraints the student does not control.

Build
  • Priority scoring across due revisions, weak topics, syllabus remaining, mock follow-ups
  • Constraint packing into the day around coaching class timings
  • A reason code on every block, shown to the student
  • Replanning when a day is missed — without cascading guilt into a 14-hour backlog
Tech
  • greedy scorerWeighted sort, fill until minutes exhausted. One day's work, ~80% of the value
  • ortools CP-SATOnly when you can point at plans the greedy version demonstrably ruins
  • celery beatNightly plan generation for every active student
Trap: rolling missed work forward indefinitely. A student who skips two days must not open the app to a 14-hour plan — that is the moment they uninstall. Decay the backlog deliberately.
P7

Narration layer

≈ 2–3 weeks

Last, not first — its entire input is the output of P2 through P6. See §5 for the model, caching and cost detail.

Build
  • Context builder assembling a bounded, single-student payload
  • Prompt templates per surface: daily nudge, weekly summary, student Q&A, parent language
  • Claim validator — every figure in the output must exist in the payload
  • Response cache keyed on a hash of the state that produced it
Tech
  • anthropic SDKclaude-opus-5, thinking: {type:"adaptive"}
  • batch APIOvernight generation at 50% cost — nudges and summaries are not latency-sensitive
  • prompt cachingStable template prefix first, volatile student payload last
  • redisState-hash cache. Unchanged state must never regenerate
P8

Parent reports, cohort intelligence, scale

ongoing
Build
  • Weekly parent report delivered on WhatsApp
  • Cross-batch and cross-institute benchmarks
  • Mastery rungs 1–2: BKT, then Elo / IRT
  • Attempts table partitioning; read replica for analytics
Tech
  • weasyprintHTML → PDF reusing the console templates
  • whatsapp BSPGupshup / AiSensy / Twilio. Templates need pre-approval — start that early
  • pyBKT · py-irtRungs 1–2, adopted only on a measured AUC improvement
  • pg_partmanMonthly partitions on attempts — the table that grows fastest by an order of magnitude
Volume math

300 students × 75 questions × 2 mocks a month ≈ 45,000 attempt rows per institute per month. At 50 institutes that is 2.25M rows a month. Partition before you need to, not after.

05 — LLM layer

Model choice is a cost decision, so make it with numbers

The narration layer is the only recurring per-student cost in the system. Everything else is fixed infrastructure, so this is where unit economics are won or lost. Three levers, applied in order: cache first, batch second, model choice last.

Available models

ModelIDContextInput /1MOutput /1M
Claude Opus 5claude-opus-51M$5.00$25.00
Claude Sonnet 5claude-sonnet-51M$2.00$10.00
Claude Haiku 4.5claude-haiku-4-5200K$1.00$5.00

The volume driver

A daily nudge per student is the high-frequency route. Assume a bounded payload of ~1,500 input tokens of computed state and ~200 output tokens of prose, at 10,000 students:

ConfigurationPer dayPer monthNotes
Opus 5, no optimisation≈ $125≈ $3,750Best narration quality, full price
Opus 5 + Batch API≈ $63≈ $1,875Overnight generation; 50% discount
Opus 5 + batch + state cachevariesmaterially lowerOnly students whose state changed regenerate
Haiku 4.5 + batch≈ $13≈ $375Cheapest; validate quality on real payloads first
How to read that table

Default to claude-opus-5 — narration is what the institute and the parent actually read, and it is the surface that makes the product feel intelligent. Batching and state-hash caching together cut the bill substantially without touching quality, so exhaust both before considering a smaller model. If you do move the daily-nudge route to Haiku, treat it as a measured decision on real payloads, and keep weekly summaries and parent reports on Opus where the writing carries more weight.

Implementation notes

  • Batch API — client.messages.batches.create() with a custom_id per student. Results arrive in any order; key by custom_id, never by position. Half price, and nightly generation has no latency requirement.
  • Prompt caching — render order is tools → system → messages. Put the stable template prefix first and the volatile student payload after the last breakpoint. Verify with usage.cache_read_input_tokens; if it stays zero, something in your prefix is changing per request.
  • Thinking — thinking: {type: "adaptive"}. Do not use budget_tokens; it is rejected on current models.
  • Structured output — where you want fields rather than prose, use output_config: {format: {...}}, not the deprecated output_format.
  • Claim validation — extract every number and proper noun from the generated text and assert each appears in the payload. This is a string scan, not a second model call, so it costs nothing and prevents the one failure mode that would destroy trust.

06 — Testing

Three test types carry this system
TypeWhat it doesWhy it matters most here
Ingestion golden filesReal (anonymised) institute exports in, expected canonical events outEvery new institute is a new format. This suite is your regression net against the messiest surface in the product.
Detector replayA known event stream in, an assertion that a specific flag does or does not fireThe highest-value tests you will write. A detector that silently stops firing is invisible until a customer asks why nobody was flagged.
Rebuild equivalenceDrop derived state, replay events, assert identical outputProves the append-only invariant holds — which is what makes model upgrades and backfills safe.

Tooling: pytest + pytest-django + factory_boy for fixtures, freezegun for the time-dependent decay and cooldown logic. Skip end-to-end browser tests until P4 — before then the console is thin enough that detector tests cover the real risk.

07 — What not to build

The scope you save is the deadline you keep
OMR sheet scanning
Institutes already have OMR vendors that export CSV. Import their output. Saves roughly a month of OpenCV work for zero differentiation.
Your own test platform
You integrate with what they run; you do not replace it. Replacing it makes you a competitor to their existing vendor and doubles the sale.
Question banks or content
The positioning is explicit: not a content play. Content is a commodity with entrenched incumbents and ongoing production cost.
Rank prediction
Institutes have been burned by vendors selling confident numbers. Refusing to predict rank is a credibility asset — say so out loud in the pitch.
Native mobile apps
Not before a PWA proves students will log at all. App-store review between you and a pilot fix is a tax you have not earned.
A feature store product
Feast and friends solve a problem you do not have. Your feature store is two Postgres tables and a nightly job.
Kubernetes or microservices
One Docker Compose file on one VPS carries the first fifty institutes. Distributed systems problems are not the ones you need.
Deep learning models early
DKT needs six figures of attempts. You will have four. Rung 0 is a window function and it is enough to sell.
The shortest honest summary

Stages P0–P3 are the product. They take about fifteen weeks, need no student to change any behaviour, and are demonstrable on files the institute already owns. Everything from P4 onward is better built against a paying pilot's real data than against your assumptions — so the objective is not to finish the roadmap, it is to reach week fifteen with something a director will sign.
