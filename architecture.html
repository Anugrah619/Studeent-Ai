01 — Core principle

The model narrates. It never computes.

This is the decision everything else hangs off. Every number a student or mentor sees — a mastery score, a mark attribution, a risk flag — is produced by deterministic code reading the feature store. The LLM receives those computed facts as a structured payload and turns them into sentences. It has no write path back into state, and no authority to produce a figure of its own.

Why this matters commercially

A coaching director will eventually ask "why did it flag this student?" A system that answers with a rule and its evidence keeps the account. A system that answers "the AI decided" loses it. This boundary is also what keeps inference cost bounded — narration is cacheable, and identical state re-renders for free.

02 — System layers

Seven layers, one direction

Data only ever moves down this stack. No layer reaches past the one below it, which is what makes each layer independently testable and independently replaceable — you can swap the mastery model without touching ingestion, or add a fourth surface without touching an engine.

03 — Data model

Every signal hangs off a topic id

The syllabus tree is the spine of the entire system. An attempt that isn't mapped to a topic is a number with no meaning; a study log without a topic is a timestamp. Get this tree right and versioned before anything else, because every table below references it and re-mapping later is expensive.

04 — Flow A

Mock result file → actionable insight

This is the highest-value flow in the system and the one most likely to be underestimated. The institute hands you a spreadsheet or an OMR export. Nine steps later a mentor sees "Aarav lost 76 marks in Chemistry, 46 of them on topics he has never revised." Everything hinges on step five.

Estimation warning

Teams building this consistently budget days for ingestion and weeks for the model. It is the other way round. Every institute's export format is different, roll numbers collide across batches, students appear with three spellings of their name, and half the papers have no chapter tags. Assume ingestion is the largest single engineering surface in phases 1–2.

05 — Flow B

Four queues, one day's plan

The daily planner is not a scheduling UI — it is a constrained packing problem. Four prioritised queues compete for a fixed number of minutes, under constraints the student does not control (coaching class timings, the exam date, how much they can actually absorb in a sitting).

06 — Flow C

The risk loop has to close

Detection is the easy half. The half that decides whether an institute renews is whether the loop closes: a flag reaches a named mentor, the mentor does something, and the system measures whether it worked. Without the return arrow you have a system that generates worry, not one that generates outcomes.

07 — Flow D

A question answered, then checked

When a student asks "why is my chemistry dropping?", the system does not forward the question to a model. It resolves intent, builds a bounded payload of that student's actual computed state, generates prose from it, then verifies that every number in the output exists in the payload before anything reaches the screen.

08 — Engines

Climb the ladder only on evidence

Each engine has a sequence of increasingly sophisticated implementations. The discipline that matters: ship the lowest rung, instrument it, and climb only when you can show the current rung failing on real data. Every rung above the first needs volume you will not have in month one.

Evaluate every rung the same way: hold out the next attempt and measure whether the model predicted it correctly (AUC). A rung that does not beat the one below it on that metric does not ship, however sophisticated it is.

Retention — spaced repetition against a deadline

Standard SM-2 and FSRS optimise for indefinite retention with minimum review cost. Exam preparation has a different objective function: maximise recall probability on one specific date, with the syllabus frozen and time strictly finite. Practically this means intervals compress as the exam approaches, and topics whose forecast recall on exam day is already sufficient get deprioritised in favour of ones that will have decayed by then. There is no off-the-shelf implementation of this — expect to modify FSRS rather than adopt it.

Mock analyzer — marks-lost attribution

The analyzer's job is to partition every lost mark into a cause, because "you scored 134" is not actionable and "98 of your 166 lost marks needed no new learning" is. Causes are inferred from time-per-question against the student's own baseline, correctness, and prior mastery on that topic:

  • Conceptual gap — wrong, and mastery on that topic was already low
  • Execution error — wrong, but mastery high and time normal
  • Time exhaustion — unattempted, and the clock ran out before reaching it
  • Avoidable skip — unattempted despite demonstrated competence on that topic

09 — Data tiers

Most of the sellable value needs no student input

"Who is actually going to enter all this data?" is the question that kills ed-tech pilots. The architectural answer is to build so that the first tier of value runs entirely on data the institute already has, and student logging is enrichment rather than a precondition.

10 — Build order

The dependencies pick the sequence

This is not a preference ordering. Each phase consumes something the previous one produces, so the graph below is close to forced. The one genuinely strategic choice is placing the director console at P3 — before the student app — which is what the tier analysis above argues for.

12 — Hard problems

Where this will actually be difficult

Listed honestly, because each of these will consume more time than the feature it sits under, and knowing that now changes how you sequence and what you promise.

1 · Question-to-topic mapping at scale

Every new test paper needs mapping before its results mean anything. The economics only work if mapping is done once per paper and reused, with LLM-proposed tags confirmed by a human rather than trusted directly.

2 · Cold start

Weakness detection needs history; a new student has none. Week one has to be useful anyway — via a diagnostic test, imported past mock results, or an explicitly provisional mode that says "still learning your pattern" rather than inventing confidence it hasn't earned.

3 · Self-reported data is unreliable

Students forget to log, log optimistically, and bulk-log a week on Sunday. Design detectors to degrade gracefully on sparse logs, cross-check self-reports against attempt data where possible, and never let a single detector depend solely on self-reporting.

4 · Attribution

When a flagged student improves, proving your intervention caused it is genuinely hard — students improve on their own, coaching happens in parallel, and everyone regresses to the mean. Staggered rollout across comparable batches is the only honest answer, and it needs to be designed into the pilot rather than reconstructed afterwards.

5 · Deadline-aware spaced repetition

As noted under Engines: no existing library optimises for recall on a fixed future date with a frozen syllabus. This is real research-flavoured work, not a dependency install.

6 · Institute syllabus divergence

Two centres teaching the same exam split chapters differently, sequence them differently, and name them differently. A single global tree will not survive the second customer; per-institute versioned trees with a canonical mapping underneath will.

The commercial risk, stated plainly

None of the hard problems above is the biggest risk to this product. The biggest risk is that students do not log data consistently, which starves every Tier 1 feature. The architecture's answer is the tier split in section 9 — make the institute-facing product genuinely valuable on institute-held data alone, so the business survives even if student adoption is mediocre.
